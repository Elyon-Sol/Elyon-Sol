# elyon-authz - the ext-authz admissibility sidecar (stand-up)

`elyon-authz` (`IMPLEMENTATION/authz_sidecar.py`) is a thin HTTP ext-authz service
that wraps the SHIPPED Elyon-Sol verifier so an OPA/Envoy deployment can enforce
envelope admissibility without writing Python. It answers ALLOW/DENY; it does not
act. Design: `docs/design/opa_sidecar_design.md`.

It reuses the production gate end to end (`ExecutorGate` -> `verify_envelope` +
the VL-076 `ReplayCache` seam). It adds no admissibility logic and no
cryptography; it is a transport adapter.

## Where it sits (Mode A)

Two ext_authz filters in one Envoy chain, admissibility BEFORE policy:

```
client -> Envoy
            |-- ext_authz #1: elyon-authz   (admissibility + envelope attestation)
            |        deny -> 403, stop
            |-- ext_authz #2: opa (opa-envoy gRPC)   (policy)
            |        deny -> 403, stop
            -> upstream service (acts)
```

`elyon-authz` answers "is this interaction admissible to be considered at all?"
(authority/coverage/integrity + attestation); OPA answers "does policy permit
it?". Each layer is independently fail-closed; neither imports the other.

## The decision contract

`POST /authz` (Envoy appends the original path, so any path under `/authz` is
answered; the decision reads only headers):

- Request headers the sidecar verifies:
  - `X-Elyon-Sol-Envelope` - canonical-JSON of the signed admissibility envelope
    (the gate sets this on its ELIGIBLE forward).
  - `X-Elyon-Sol-Interaction` - canonical-JSON of the gate-normalized interaction
    (the DEFAULT attested-forward extractor; design section 5).
- Response:
  - `200` + `x-elyon-decision: ALLOW` on accept.
  - `403` + `x-elyon-decision: DENY` + `x-elyon-reason: <REF_*>` on refuse.
  - `403` + `REF_TARGET_*` on any internal/anchor/parse/config error - fail
    closed, never a 5xx-as-allow.

A direct, un-attested caller (no envelope header) is denied
`REF_VERIFY_ENVELOPE_ABSENT`. `GET /healthz` is liveness only and reports no
trust state.

## Configuration (out-of-band, never from the repo)

Parity with `reference_target.config_from_env` and the `*_from_env` seam:

| Env var | Meaning |
| --- | --- |
| `ELYON_TARGET_URL` | the target identity envelopes bind to (must equal the admit `target_url`) |
| `ELYON_RECORD_PATH` | local path to the published-record bytes (`published_hashes.json`) |
| `ELYON_PINNED_ROOT_SHA256` | the out-of-band published-record anchor (sha256 of the authentic bytes) |
| `ELYON_GATE_KEY_ID` | the pinned gate signing key id |
| `ELYON_GATE_PUBLIC_KEY_HEX` | the pinned gate signing public key (raw Ed25519 bytes, hex) |
| `ELYON_CLOCK_SKEW_SECONDS` | optional non-negative skew tolerance (default 0) |
| `ELYON_REPLAY_REDIS_URL` | optional shared Redis for cross-instance exactly-once replay |

Any required value absent / malformed -> the sidecar fails every `/authz` closed
(`REF_TARGET_NOT_CONFIGURED`). Secrets arrive by environment (from the
out-of-band `.env` generated by `deploy/bootstrap_config.py`); nothing is baked
into the image.

For horizontally-scaled deployments, point every replica at one
`ELYON_REPLAY_REDIS_URL` so a `decision_id` honored on any replica is refused on
every other (replay defense across instances).

## Stand up

The sidecar reuses `deploy/Dockerfile` (one image, command override to
`IMPLEMENTATION.authz_sidecar:app`).

```
cd deploy
python bootstrap_config.py        # writes .env: gate key pin + pinned anchor
envoy --mode validate -c envoy.example.yaml   # validate the proxy config
docker compose -f docker-compose.yml -f docker-compose.authz.yml up --build
```

Smoke test (a real attested request is minted by the gate on `/governed-call`,
then presented to the sidecar with the two headers):

```
# ALLOW: present a freshly-minted envelope + its interaction.
curl -i -X POST localhost:9200/authz \
  -H "X-Elyon-Sol-Envelope: <canonical-json envelope>" \
  -H "X-Elyon-Sol-Interaction: <canonical-json interaction>"
# -> 200, x-elyon-decision: ALLOW

# DENY (un-attested): no envelope header.
curl -i -X POST localhost:9200/authz
# -> 403, x-elyon-reason: REF_VERIFY_ENVELOPE_ABSENT
```

## Validation status

The Python service + its refusal matrix are verified in-container by
`TESTS/adversarial/test_authz_sidecar.py` (allow; deny on each REF_* class;
fail-closed on absent/bad config; replay across two sidecar instances). The
`docker compose` stand-up and `envoy --mode validate` are the author's locus
(no docker / no envoy binary in the build sandbox), the same posture as the
C1/C2 deploy artifacts (artifact 13). This is the in-house build; a real OPA-shop
integration on a live surface is the separate G5 track.
