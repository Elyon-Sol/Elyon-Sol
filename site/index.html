Pre-execution admission control · canon v0.9.8.4

A gate that decides whether an action is allowed
to happen — before it happens.

Elyon-Sol is a deterministic, fail-closed HTTP admission gate derived from a formal admissibility specification. Given a request and a SHA-256-pinned manifest, it returns ELIGIBLE only if the caller's authority and operation sets satisfy the manifest and the continuity invariant holds — otherwise it refuses, and the upstream is never called.

What it is

An authorization boundary for actions, not just requests

The gate constructs an admissibility envelope on every ELIGIBLE decision — a content-hashed record of the full decision context (canon, manifest, evaluator, request, condition results, timestamp), signed with the gate's key. The upstream target performs an action only if the request carries a valid, current, correctly-bound, single-use envelope. The canon defines three invariants, all fully implemented:

AC³ Authority

The caller's authority set must satisfy the manifest's required authority set. Canon §§11.3, 11.5.

T²⁶ Coverage

The caller's operation set must be covered by the manifest's required operation set. Canon §§11.4, 11.6.

CCS Continuity

Eligibility does not persist across state transitions; any change to canon, manifest, or evaluator invalidates a prior ELIGIBLE. Canon §§12–13.

Key features

What the system enforces

⛔ Fail-closed by design

On REFUSE or any exception the upstream is never called. It trades availability for safety — when it cannot be sure, it refuses.

✒️ Signed admissibility envelope

Every ELIGIBLE decision is bound into an Ed25519-signed, content-hashed record over canonical JSON — tamper-evident and verifiable target-side.

🔗 Action & body binding

A decision binds to exactly one target and one action — down to the executed request bytes — so a token minted for action A cannot release action B.

1️⃣ Single-use replay defense

Each envelope is honored once. A shared-store replay cache fails closed at startup under horizontal scale without a coherent backing store.

👤 Human-oversight governance

High-impact actions return 202 PENDING_APPROVAL and are held until a separate human approver signs a grant — separation-of-duties enforced by role in the signed key record.

🛡️ Non-bypass topology

mTLS client-auth proves the gate is the only authorized caller of the target; an OPA/Envoy ext-authz sidecar answers ALLOW/DENY reusing the production verifier.

⏱️ Freshness & clock-skew

Signed published-record freshness plus a configurable clock-skew window; a stale or out-of-window record is refused rather than trusted.

🔑 Key provenance & rotation

Approver and issuer trust is resolved from a signed key-record chain; publisher keys are rotatable live under a no-secret-in-history protocol.

🧾 Auditable & reconcilable

An issuance/approval log lets every held-and-forwarded high-impact decision be reconciled — a forward without a recorded grant is a caught invariant violation.

vs capability-token systems — the honest comparison

The table above is against access-control styles. The sharper question is against systems that already issue signed, bound tokens — macaroons, biscuit, SPIFFE/SVID, GNAP, and the IETF Transaction Tokens draft. Stated plainly: an admissibility envelope is a capability token — signed, action-bound, single-use — and Elyon-Sol claims no new cryptographic primitive. What it adds is behavioral: the envelope is a receipt of a policy decision (it pins the exact canon, manifest, and evaluator that decided), it self-invalidates when that policy changes, it makes human approval a cryptographic separation-of-duties primitive, and it ships with a live public break-it challenge. It composes with these systems — it can run on top of a biscuit rather than instead of one.

Break it in 60 seconds

The attacking surface is public. Poke it right now with nothing but curl and jq — no signup, no gatekeeping. See a valid flow work, then try to break it; crediting a confirmed break is one email away.

A confirmed break — making the target act, or the sidecar answer ALLOW, on a call that should be refused — would be the first external result this project has ever had. Confirm your break with the inspector (the tool decides, not us), then email security@elyon-sol.io.

1 · Mint a real token from the gate
INTERACTION='{
  "AP": ["identity","role"],
  "OP": ["session","request"],
  "context": {
    "tool": "transfer_funds",
    "args_sha256": "ee0885070ca8ca1ff7df3e53275c4cadb3fbf747f3e0ea380a002f8c69ab8e9d"
  },
  "expected_manifest_version": "1.0",
  "expected_manifest_sha256": "a21dea8b79d459bd700ca44a30c2ca4a6efbee1447708cbc12c0bbb322d823b8"
}'

ENV=$(curl -s https://gate.elyon-sol.io:8443/governed-call \
  -H 'content-type: application/json' \
  -d "{\"target_url\":\"https://target.elyon-sol.io:9443/target\",\"interaction\":$INTERACTION}" \
  | jq -c '.envelope')
2 · Present it once — the target acts (this is the control, not a break)
curl -s https://target.elyon-sol.io:9443/target \
  -H "X-Elyon-Sol-Envelope: $ENV" \
  -H 'content-type: application/json' \
  -d "$INTERACTION" | jq
# expect: {"honored": true, "reason": "REASSERTED_AND_BOUND"}
3 · Now try to break it — every one of these SHOULD be refused
# a) no token at all
curl -s https://target.elyon-sol.io:9443/target -H 'content-type: application/json' -d "$INTERACTION" | jq

# b) replay the same valid token a second time
curl -s https://target.elyon-sol.io:9443/target -H "X-Elyon-Sol-Envelope: $ENV" -H 'content-type: application/json' -d "$INTERACTION" | jq

# c) forge — tamper one byte of the signed envelope
FORGED=$(echo "$ENV" | jq -c '.decision_sha256 = "deadbeef"')
curl -s https://target.elyon-sol.io:9443/target -H "X-Elyon-Sol-Envelope: $FORGED" -H 'content-type: application/json' -d "$INTERACTION" | jq

# d) rebind — reuse the token but claim a different action
REBIND=$(echo "$INTERACTION" | jq -c '.context.tool = "delete_database"')
curl -s https://target.elyon-sol.io:9443/target -H "X-Elyon-Sol-Envelope: $ENV" -H 'content-type: application/json' -d "$REBIND" | jq

# e) sidecar — get authz to ALLOW any of the above (200 = finding, 403 = working)
curl -s -o /dev/null -w "%{http_code}\n" https://authz.elyon-sol.io:9243/authz \
  -H "X-Elyon-Sol-Envelope: $FORGED" -H 'content-type: application/json' -d "$INTERACTION"

Expected: b–e all refuse — REF_VERIFY_REPLAY, REF_VERIFY_SIGNATURE_INVALID, REF_VERIFY_BINDING_MISMATCH, and a 403 from the sidecar. Make any of them act, and you take first blood.

The sharper edges. Those five are the easy cases and they refuse. A real break in a system like this lives in an implementation seam — where the gate and the target disagree about what a request means. The classes worth your time: canonicalization mismatch (reordered or duplicate JSON keys, raw vs escaped unicode, NFC vs NFD, 1 vs 1.0), a field the signature does not cover (mutate one field at a time), single-use under real concurrency (present the same token many times at once, not in sequence), validity-window edges (a token expired to one host but not another), and cross-binding (a token minted for A honored for B). Full attack brief: deploy/BREAK_IT.md.

Red-team solicitation

Break Elyon-Sol — open challenge for security freelancers

We run a gate that refuses any action that does not carry a valid permission to act. We think you cannot make it act on something it should not. We are asking you to try — a confirmed break is a real result, and it is credited, named, and written permanently into the project's public record.

The claim to disprove. Without the gate's signing key, there is no request you can craft that (a) makes the target perform an action, or (b) makes the sidecar answer ALLOW, unless the token in the X-Elyon-Sol-Envelope header is validly signed, currently valid, bound to exactly that action and target, and not previously used. Using a real token once, as intended, is not a break — that is it working.
Why trust this. We won't oversell it — that's the point. It hasn't been externally validated, and we say so: every test to date is ours, and internal evidence is not validation. The tool adjudicates, not the author — a read-only inspector reads your token the way the target does and rules on whether you broke it. The claim is one falsifiable line, and we publish the boundaries we do not defend so we can't move the goalposts. It's all on the public record: formally specified, open source (AGPL), a citable DOI, and a ledger that logs our own corrections.

What counts as a break

  • Target break — get target.elyon-sol.io to act (its GET /received count increments) on a request whose token is absent, forged, expired, replayed, altered, or bound to a different action/target.
  • Sidecar break — get authz.elyon-sol.io to return 200 / ALLOW for a request that is not a currently-valid, correctly-bound, single-use, validly-signed token.
  • Reproducible from your steps — one reproduction beats any description.

Out of scope (please don't spend time here)

  • Denial of service, flooding, availability — refusing is the design, not a break.
  • Stealing the signing key, or compromising host OS / cloud / TLS by means outside the request protocol (welcome as separate, credited infra reports).
  • Acting on a genuinely valid, unused token — that is correct behavior.
  • "An authorized action could be unwise" — the gate checks authorization, not wisdom.

How to start & submit

  • Mint a sample token: POST /governed-call on the gate, present it once to the target/sidecar to see a valid flow.
  • Then attack the edges — drop the header, alter a field, replay, expire, re-point at another action/target, fabricate.
  • Confirm a break with the inspector before you submit — the tool decides, not us: python IMPLEMENTATION/envelope_inspector.py inspect token.json. If it rates your token invalid, expired, replayed, or rebound and the target acted anyway, that gap is the finding — settled before we even reply.
  • Send it to security@elyon-sol.io: the class (target / sidecar), the exact requests in order, and what you saw (status codes, the /received count). We reproduce, classify, and respond.
